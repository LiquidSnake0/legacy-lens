What there is to decide about the frameworks themselves

The names nothing accounts for come to 4 questions. What follows is what each one was for, what replaced it, and what there is to choose between. None of the options is a recommendation: which one is right depends on how many people, how much time, and whether the old and the new have to run side by side, and none of that is in the code.

The request context. 109 calls through RequestContext, HttpContextBase, HttpRequestBase, HttpResponseBase, HttpCookieCollection, HttpContextWrapper, and 3 more.

System.Web wrapped the request in a family of abstract base classes so that code could be tested against them, and passed one around as the ambient state of the request. ASP.NET Core has HttpContext and its parts, injected rather than ambient, with different names and a different shape. An uploaded file is IFormFile, cookies are IRequestCookieCollection, and there is no HttpException.

  • Move the code onto the new types directly. Shortest where the class already receives the context as an argument.
  • Put an interface of your own in front of what you actually use, and implement it over the new types. Longest, and the only option that lets the old and the new code run side by side.
  • Push the context out of the class entirely and pass the values it reads. Turns a migration into a design change, which is sometimes the right trade and never a small one.

Pipeline internals. 72 calls through MvcRouteHandler, HttpApplication, MvcHandler, ControllerBuilder, ReflectedControllerDescriptor.

Code that reached into how MVC found controllers, resolved views or handled the application lifetime. Global.asax is the usual entry point. There is no equivalent, and that is deliberate: the pipeline is middleware you compose in Program.cs rather than handlers you replace.

  • Find what the code was working around and check whether the new pipeline does it already. Most of these predate features the framework grew.
  • Write it as middleware, which is where the behaviour belongs now.
  • Treat it as a rewrite of that concern, and price it as one. This is the group that genuinely costs.

Areas. 7 calls through IRouteWithArea.

An area registered itself by deriving from AreaRegistration, and the framework found it by scanning assemblies at startup. Areas still exist and there is nothing to register: a controller carries [Area] and routes name it.

  • Delete the registration classes and put [Area] on the controllers.
  • Ask first whether the areas earn their keep, because the routing they were working around is gone.

Model binding extensibility. 6 calls through ModelBinderDictionary, DefaultModelBinder.

Binding was extended by deriving from the default binder or replacing the metadata provider, both of which knew a great deal about the pipeline around them. ASP.NET Core binds through IModelBinder and IModelBinderProvider, registered in options. The shape is similar and the base classes are not there to derive from.

  • Write the binder against the new interfaces. Usually smaller than the original, because the default no longer has to be reimplemented around it.
  • Check first whether the framework now does it. Several of these existed to bind types that bind on their own today.
